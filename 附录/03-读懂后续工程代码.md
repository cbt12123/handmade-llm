# 读懂后续工程代码

第一部分介绍了基础语法，后续源码把它们组合成可恢复的 Agent 和模型服务。这一页只解释项目里实际出现、容易卡住的写法，不要求一次读完。第21～25章优先看第1、2、5节，第34章看第3、4节，第35章按需看第6节。

这里的短 Python 代码块可分别运行；命令行示例使用附件脚本。基础例子只用标准库，不启动服务、不加载模型，也不写入你的学习记录。

## 1. 嵌套数据与复制：一次修改影响哪里

Agent 的状态是字典，字典里还有列表和其他字典。例如：

```python
state = {"step": 0, "events": [], "grades": {"gd-01": 1.6}}
print(state["grades"]["gd-01"])  # 1.6
state["events"].append({"action": "grade", "ok": True})
print(len(state["events"]))  # 1
```

`state["grades"]` 先取到内部字典，再用题号取得数值。`append` 修改原列表，不创建一个新状态。

**直接赋值共享对象，浅复制只复制外层，深复制还复制这里的嵌套可变数据。** 先看结果，再理解为什么：

```python
import copy

state = {"step": 0, "events": []}
shared = state
shallow = state.copy()
candidate = copy.deepcopy(state)

shallow["events"].append("shared event")
candidate["events"].append("candidate event")
assert shared is state
assert state["events"] == ["shared event"]
assert candidate["events"] == ["candidate event"]
```

`shallow` 是新字典，但内部 `events` 仍是原列表。`candidate` 的列表独立，因此失败后可以丢弃候选状态。第25章的 Agent 会先深复制，再尝试动作，成功才接受候选。深复制不是所有对象都适用的万能方法；数据库连接与模型等资源不放进这种可序列化状态。

源码中还会看到两种短写法：

```python
state = {"step": 0, "status": "running"}
state.update(step=1, status="done")
events = [{"action": "search"}, {"action": "search"}, {"action": "finish"}]
completed = {event["action"] for event in events}
assert state["step"] == 1
assert completed == {"search", "finish"}
```

`update` 修改已有字典，返回 `None`，不要写 `state = state.update(...)`。花括号内没有冒号的推导式在这里生成集合，用来去重和检查“哪些动作出现过”，不保留重复次数或顺序。

## 2. 参数、默认值与命令行入口

函数的关键字参数与命令行参数属于不同入口：

```python
def run(request, allow_record=False):
    return {"request": request, "allow_record": allow_record}

result = run("检查答案", allow_record=True)
assert result["allow_record"] is True
```

`False` 是未指定参数时的默认值；`allow_record=True` 是这次调用给出的值。默认值在定义函数时确定，所以可变的默认列表或字典需要格外小心。

命令 `python ... --steps 3` 是给脚本传入字符串，脚本里的 `argparse` 再把它解析成整数。完整例子见[cli_demo.py](../assets/appendix/cli_demo.py)：

```powershell
python assets/appendix/cli_demo.py --steps 3
python assets/appendix/cli_demo.py --steps 3 --allow-record
python assets/appendix/cli_demo.py --help
```

第一条输出 `{"steps": 3, "allow_record": false}`；第二条中的开关把值变为 `true`。`--allow-record` 后面不需要再写 `True`，因为附件使用 `action="store_true"`。

`if __name__ == "__main__":` 使入口只在直接运行文件时执行。其他文件 `import` 它时，可以取得函数，而不会自动执行命令行流程。实际 Agent 的参数更多，结构仍是“读取参数 → 创建对象 → 调用函数 → 显示结果”。

## 3. 异常、finally 与 with：失败后仍然收尾

**`finally` 中的收尾会在正常结束、提前返回或异常离开时执行。** 下面用普通字典演示临时改动与恢复：

```python
settings = {"backend": "baseline"}
original = settings["backend"]
try:
    settings["backend"] = "fused"
    raise ValueError("用于检查恢复的异常")
except ValueError:
    print("发现异常")
finally:
    settings["backend"] = original
assert settings["backend"] == "baseline"
```

`except` 在这里处理预期的异常；`finally` 恢复临时状态。不要在真实程序中用宽泛捕获把错误静默忽略，读者还需要知道具体哪一步失败。

`with` 表示进入和离开一个受管理的范围，不只用于文件。第34章将模型方法的替换包成一个上下文管理器：

```python
from contextlib import contextmanager

@contextmanager
def temporary_backend(settings):
    original = settings["backend"]
    settings["backend"] = "fused"
    try:
        yield settings
    finally:
        settings["backend"] = original

settings = {"backend": "baseline"}
with temporary_backend(settings) as current:
    assert current["backend"] == "fused"
assert settings["backend"] == "baseline"
```

按执行顺序读：先运行 `yield` 前面的代码；把 `yield` 的对象交给 `as current`；暂停函数，执行 `with` 内部；离开时继续执行收尾。这里的 `yield` 不是“立刻结束整个函数”的 `return`。发生异常也会进入 `finally`，恢复原值。

真实代码替换的是模块的 `forward`，不是这个字典。这个例子帮助理解范围和恢复顺序，不能据此断定真实替换已经成功或速度有收益；第33、34章另有调用证据与对照实验。

## 4. 装饰器、循环中的函数与绑定方法

`@装饰器` 表示在定义函数时，把函数交给另一个函数处理。在上一节，`@contextmanager` 让包含 `yield` 的函数可以用于 `with`。在服务中，`@app.post(...)` 把函数注册成请求处理入口。作用取决于具体装饰器，不能仅根据 `@` 判断函数何时执行。

第34章在循环里定义替换函数，为什么写 `_original=original`？先看更小的例子：

```python
functions = []
for offset in (1, 2):
    def add(x, saved=offset):
        return x + saved
    functions.append(add)
assert functions[0](10) == 11
assert functions[1](10) == 12
```

每次定义时，默认参数保存这次的数值。如果改成直接在函数体里读取循环变量 `offset`，等循环结束再调用时，两次都会读取最终的 `2`。实际替换函数用默认参数保存每个模块自己的原始方法，防止都引用到最后一个模块。

类方法中的 `self` 是当前对象。`types.MethodType(forward, module)` 将一个函数绑定到 `module`，以后调用时自动把这个模块作为 `self` 传进去。[model_adapter.py](../script/part06/model_adapter.py)先保存原始绑定方法，再执行替换，离开范围时恢复。先理解这条顺序，再研究底层的 Python 方法机制。

## 5. JSON、HTTP 与数据库：检查分层进行

JSON 是文本格式，Python 字典是内存对象。把模型返回的字符串解析成字典，只完成第一层检查：

```python
import json

text = '{"action": "search", "args": {"query": "梯度"}}'
action = json.loads(text)
assert isinstance(action, dict)
assert action["action"] == "search"
assert isinstance(action["args"]["query"], str)
```

接下来还要检查动作名是否允许、参数字段与类型是否符合要求、内容是否在范围内、当前状态是否授予权限。JSON 合法，不代表可以执行。第21、22章分别解释动作协议与权限。

HTTP 请求的检查顺序是：连接是否成功 → 状态码是否表示成功 → 响应能否解析 → 结构与业务取值是否有效。`response.raise_for_status()` 检查 HTTP 错误，`response.json()` 解析响应正文，两者都不能替代工具参数验证。具体请求例子在第18、21章，这里不需要额外启动服务。

第25章的 `with self.store.db:` 管理 SQLite 事务。在没有异常时提交这一组数据库操作，异常离开时回滚。**它不会自动撤销 Python 列表的修改，也不会撤回已经发出的 HTTP 请求。** 所以 Agent 还需要候选状态与明确的副作用边界。

数据库连接的这个 `with` 也不会自动关闭连接；连接关闭由项目自己的 `close()` 和服务收尾负责。看到 `with` 时，应先确认对象到底管理什么，不要把所有上下文管理器都理解为“关闭文件”。

## 6. 类型标注与 async：读到服务入口再补

普通 Python 中，下面的标注说明接口意图，并不会自动拦住错误类型：

```python
def identity(value: int) -> int:
    return value
assert identity("text") == "text"
```

Pydantic 请求模型会读取标注并在接口边界执行校验，这是库提供的行为。第35章的 `Literal['baseline', 'fused']` 限定请求后端的两个取值，`Field` 描述长度与数值范围；不要把这种框架校验推广成“所有 Python 标注都会检查”。

`async def` 定义异步函数，配合 `await` 在合适位置等待异步操作。它不自动把计算送到 GPU，也不保证推理可以并行。第35章使用 `@asynccontextmanager` 定义服务生命周期：`yield` 前加载和预热，`yield` 后是退出阶段；这个 `yield` 不是向 HTTP 客户端输出生成 token。

服务中的请求处理仍有自己的并发边界。先读“启动一次加载模型 → 请求复用模型 → 退出收尾”的顺序；若要设计流式输出或并发服务，需要另学相应接口与调度机制。
